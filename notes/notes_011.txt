1. PURPOSE
Live-verification checkpoint for the batched testing cadence adopted this
session (ROADMAP.md "Testing cadence"): after five code-only releases
(1.3-1.7), run real Repomix + real Anthropic API calls to confirm the batch
actually works, before starting the next batch. User explicitly authorized
real API spend for this checkpoint ("go ahead with the real tests and push
afterwards").

2. METHOD
No dedicated Windows desktop-automation tool is available in this
environment (only a browser-scoped `computer` tool exists, per prior
sessions' notes). Rather than reuse the earlier approach of simulated
mouse clicks via PowerShell/user32.dll, this checkpoint drove the real
`ScaffoldingApp` class programmatically: instantiated the real class,
ran its real `app.mainloop()`, and scheduled each test step via
`app.after(...)` (the same thread-marshaling mechanism the app itself
uses for `update_status`/`reset_buttons`), rather than manually polling
with `app.update()` in a loop. Anthropic's `Messages.create` was wrapped
(not replaced) purely to count real calls; every call still went through
to the real API. This is a more faithful, more repeatable live test than
pixel-coordinate clicking, at the cost of not visually confirming pixel
rendering for every element (see section 5).

First attempt used a manual `app.update()` poll loop instead of
`mainloop()` and hit `RuntimeError: main thread is not in main loop` when
the worker thread called `self.after(0, ...)` — a harness bug, not an app
bug (real usage always calls `app.mainloop()`, which this harness initially
didn't). Confirmed zero cost from the failed attempt: the crash happened at
the `update_status("Generating agents.md...")` call, before any
`client.messages.create()` was reached; no temp XML was left behind, no
orphan process, output files unchanged. Fixed by rewriting the harness
around `app.mainloop()` + `app.after(...)`-scheduled steps.

5. NOT DONE (deliberately) / KNOWN GAPS
- The close-during-job confirmation dialog (`_on_close`, v1.3/v1.5 copy)
  was NOT triggered live. `messagebox.askyesno` is a real blocking native
  modal in this environment; dismissing it programmatically would need a
  simulated OS-level keystroke/click with no desktop-automation tool
  available, and a wrong keybinding assumption or a stolen-focus terminal
  window (a documented risk in this environment per MEMORY.md's earlier
  operational note) could hang the session on an un-dismissable dialog.
  Given the dialog is a single well-tested stdlib call with a plain string
  argument, already source-reviewed three times (notes_006/007/008), the
  risk of forcing a live click-through outweighed the marginal value here.
  Remains code-review-verified only, same category of gap as prior
  sessions' "not GUI-tested" notes.
- No visual/pixel screenshot was taken anywhere in this checkpoint —
  verification used `.cget()` widget-state assertions instead, which are
  more precise than eyeballing a screenshot for the properties that
  matter (exact text, exact enabled/disabled state) but do not prove
  something is visually legible, correctly positioned, or not clipped/
  overlapping on screen. If a future release changes layout significantly,
  a real visual pass is still worth doing.
- Only the default project (this repo, via the remembered `Other...` path
  in `last_project.json`) and the default model (Haiku 4.5) were exercised.
  Other projects/models were not live-tested this checkpoint.
